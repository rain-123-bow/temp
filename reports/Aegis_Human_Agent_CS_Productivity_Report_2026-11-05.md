# 人 × Agent（Aegis 标准）任务产出评估报告

> **案例：PROCESS V3 — Windows Client / Ubuntu Server 第一阶段软件研发**  
> **版本：V1.0 / 2026-11-05**  
> **证据截止：2026-11-05 20:40（按任务日志所示时刻；时区未独立验证）**  
> **用途：Aegis 落地案例分析、工程管理复盘、后续对照实验设计**  
> **证据性质：单案例、非受控对照；含传统工程量情景估算。**

## 执行摘要

**结论 1 — 交付效率在工程量级上表现突出。** 第一阶段完成了可运行的 Windows 桌面 Client、Linux Server、独立 Scheduler.Sim、真实可信通信诊断、软件控制与恢复约束，以及多层测试和发布材料。Agent 任务日志累计 **43 小时 27 分 03 秒（43.4508 h）**，跨 **6 天 11 小时 11 分（155.1833 h）**。这不是完整生产系统的交付时间。[U1][S1][S2][S3]

**结论 2 — 传统人工基线只能做条件估算。** 本报告按**相同已完成软件范围、相似验收深度**建立自下而上的人工工作分解：**400 / 600 / 900 人时**（精简/中心/审慎情景）。对应“传统人工人时 ÷ Agent 任务日志小时”的**名义工时量级比**为 **9.2 / 13.8 / 20.7 倍**。该数值**不是**经过对照实验测出的开发加速率，也不是 Aegis 相对于裸 Codex 的增益。[M1]

**结论 3 — 人类交互投入较低，但真实人工总投入未知。** 另一张截图估算对话输入与阅读为 **3 小时 15 分**，其计算范围 **2 小时 44 分至 4 小时 06 分**，且未覆盖独立阅读、架构思考、人工终端操作、环境配置及实机检查。以 3.25 h 直接相除会出现 **123–277 倍**的条件人力杠杆，但**不能作为实测人效、节省工时或对外宣传数字**。[U2]

**结论 4 — 高难度集中在可靠性，而非界面数量。** 多身份和独占控制、跨进程三通道通信、原 ID 幂等、任务与连接生命周期分离、未知结果对账、存储降级和严格恢复隔离，构成主要工作量。UI 只是可见的一个部分。[S1][S2]

**结论 5 — 质量证据有分层，必须保留未完成项。** G3 受限矩阵 48/48 通过；G5 的单站 900 秒与四站 300 秒软件合成负载在最终候选通过；真实 C/S 10 分钟连接无意外断开，但 600 个预定 time 槽漏 1 个，严格结果 **INCOMPLETE**。主界面仍是 Mock，正式 A–F、生产 Scheduler/SDK、硬件、完整业务联调均未完成。该案例证明的是**高强度软件阶段的产出能力**，不是产线投放能力。[S1][S3]

**对 Aegis 落地的判断：** 可以作为“高复杂度软件阶段的高产出个案”与后续评估基线；不能单靠它证明 **Aegis 专属增益、行业平均加速倍数、生产可靠性或商业 ROI**。优先补齐个人实际工时、Agent 用量成本以及与“人工+原生 Codex”相同验收口径的对照数据。

## 2. 复杂度分析：难在失败状态的组合

### 2.1 复杂度来源与影响

| 维度 | 相对评价 | 关键机制与为什么费时 |
|---|---|---|
| 功能广度 | 中高 | 多页 UI、账号/权限、任务/工艺包、历史、日志、安装维护，跨功能测试面较宽 |
| 架构耦合风险 | 高 | Client / Server / 独立 Scheduler 的职责强约束；Server 不能伪造源执行结果 |
| 并发与状态空间 | 很高 | 独占接入、接替、断连、重启、迟到回执、权限撤销同时发生时必须维持正确因果 |
| 数据一致性 | 很高 | 原 ID 语义、请求与效果分离、outbox 对账、库存严格相等与恢复门 |
| 故障处置 | 很高 | 存储降级、受限原对象结束、unknown 不重做、fault/cleanup/recovery 有不同证据 |
| UI 工程 | 中 | 自绘桌面布局、局部滚动、状态隔离、资源边界；主要难点是工程细节而非渲染研究 |
| 测试验证 | 很高 | 独立进程、故障模拟、版本闭包、负载、发布/回滚、实际跨机连接及原始证据保留 |
| 物理与生产风险 | **尚未测评** | 真实 Scheduler/SDK/机械臂、实际停止/释放、现场性能和生产身份体系未完成；不可给生产质量评分 |

上述定性分级仅为**本报告的工程判断**，不属于行业统一复杂度量表；它也不意味着每项能力都在最终同一二进制上完成穷举验收。

### 2.2 为什么同一功能会形成多个困难场景

以“管理员接替正在运行的任务”为例：一站只允许一个控制者；合法新管理员必须先确认，随后原子切换控制代次；旧连接的新输入失效；原任务/包/参数/进度、已接纳但未派发 outbox、审计发起者继续保留；接替本身不得添加 stop、withdraw、recover、query 等源端动作。管理员取消、老连接断开、源返回迟到、Server 重启等分支必须分别处理。[S1§5][S2§14]

以“响应丢失后的执行请求”为例：HTTP 成功只证明服务器响应，accepted 只证明受理；命令可能已经交给 Scheduler。系统不能重新分配 ID 盲目重发，应按原 ID 和源持久身份核查。当源记录覆盖不足时，正确结果可能一直是 unknown，而不能伪装成功或失败。[S1§9][S2§16]

以“数据库恢复后是否解锁业务”为例：备份文件完整并不证明恢复时源端无新增命令。恢复在 quarantine 状态中核对全命令集合、任务状态、源代次和可信证明；任何不完整或仍活跃对象阻断 finalize。该软件机制的设计/验证复杂度高于普通 CRUD 恢复。[S1§11][S2§24]

**工程难度的主要驱动：** 正常路径代码量有限；每增加一个独立故障源、代际或权限边界，测试组合明显增加。由于没有完整的状态空间枚举，本报告不计算“组合数”等伪精确指标。

## 3. 传统研发人时：可审计的工作分解估算

### 3.1 估算假设

- **工程师基线：** 有相关经验的 C#/.NET 桌面与 Linux 服务端工程师；可以使用 IDE、调试器、现成框架和普通脚本，不假设完全手写密码学或 HTTP/IPC 底层。
- **相同验收边界：** 达到当前“软件阶段已证明”的功能、测试和交付证据；不完成未授权的正式 A–F 与硬件产线验证。
- **单位：** *人时*是全部人的投入之和，研发、测试、评审、故障修复各算一次；团队并行可减少日历时长，不能自动减少人时。
- **数值性质：** 下表是基于已交付功能拆分的低/中/高**情景赋值**，并未来自同一项目的人工对照实验或经过校准的生产率数据集；不能把情景跨度解释为统计置信区间。

### 3.2 工作分解（WBS）

估算的主要不确定性来自三项：是否已有可复用的基础通信/身份库；工业状态机设计者对幂等/恢复的熟悉程度；测试工具和发布环境是否现成。**任何一种情景都不能称作“行业正常用时”或“传统平均用时”。**

### 3.3 传统项目的时间结构

在中心情景 **600 人时** 下，若按每人每日 8 小时计算，相当于 **75 人日**。一个人串行执行约 75 个工作日；两人理想完全平行约 37.5 工作日；三人理想完全平行约 25 工作日。后两项只是*人日除以人数*的算术下界，尚未计入依赖、协调和评审阻塞，不能预测真实排期。

对照历史 AI 研究也不能自动获得人工基线。研究测量的是不同工程师、工具、任务和时间窗口下的平均处理变化，不是这个工业 C/S 案例的人工实现总时长。[E1][E2][E3]

### 4.2 人类交互量与估算的适用范围

另一张统计截图给出：**127 条普通消息、约 6857 个非空字符、18 次表单回复、回答 19 个问题、提供 20 张图片**；按“输入 40–60 字/分钟，阅读约 30071 字、400–600 字/分钟”的假设，输入约 **1 h 54 min–2 h 51 min**，阅读约 **50 min–1 h 15 min**，合计 **2 h 44 min–4 h 06 min**，中心粗估 **3 h 15 min**。[U2]

这个值有两个不同的不确定性：**速度假设不确定**（实际上可能语音、复制粘贴、跳读或反复读），**活动覆盖不完整**（图文检查、审查代码/测试材料、终端操作、思考、现场沟通不在计数中）。因此不能据此得出用户总工时=3.25 h，更不能用它直接计算已验证的人力 ROI。

用户另述 UI 在一个下午完成、其他部分在两个较集中工作日内完成（不计睡眠）。这是工作节奏的自述；与日志总跨度 6 天 11 小时不矛盾，但无法据此复算每一天的人类有效工时。[U1][U2]

## 5. 产出效率：四种时间/资源指标必须区分

### 5.1 可算，但不能误命名的名义压缩系数

定义：

`R_log = 假定传统研发人时 / Agent 日志任务小时 = B / 43.450833...`

| 传统人工情景 B | Aegis 日志任务时长 | **R_log** |
|---:|---:|---:|
| 400 人时 | 43.4508 h | **9.21×** |
| 600 人时（中心） | 43.4508 h | **13.81×** |
| 900 人时 | 43.4508 h | **20.71×** |

**解释：** 这是“估计人工工作量相对于 Aegis 日志任务时长”的条件比值。分子的单位是人力劳动、分母是平台日志时长，**不能直接叫严格交付加速比或 Agent 资源效率**。若日志任务时长与真实并发/等待结构不一致，压缩系数会变化。[M1]

### 5.2 人力杠杆的敏感性：真实人工时长尚未实测

定义：`R_human = B / H_total`，其中 `H_total` 必须包含全部人工需求决策、审查、交互、终端/实机操作、异常处理和交付验收，而不只包含聊天。

| 假设实际人类投入 H_total | 400 人时基线 | 600 人时基线 | 900 人时基线 |
|---:|---:|---:|---:|
| 3.25 h（仅截图中心粗估，**不能认定为总量**） | 123.1× | 184.6× | 276.9× |
| 6 h（条件示例） | 66.7× | 100.0× | 150.0× |
| 10 h（条件示例） | 40.0× | 60.0× | 90.0× |
| 15 h（条件示例） | 26.7× | 40.0× | 60.0× |
| 24 h（条件示例） | 16.7× | 25.0× | 37.5× |

这张表是**敏感性分析，不是对真实劳动产出的五次观测**。即使真实人工时间确认，仍需人工对照基线才能给出因果意义上的提升幅度。

### 5.3 交付速度与经济效率：当前不能给单点倍数

| 想衡量的指标 | 正确定义 | 当前是否可算 |
|---|---|---|
| 名义日志工时量级比 | 估算人工人时 ÷ 43.4508 h | **可作条件演示**：9.21–20.71× |
| 人力节省 / 人力杠杆 | 同范围人工人时 ÷ 实际完整个人/团队人时 | **不可实测**：完整人工 H 未采集，基线未对照 |
| 交付延迟加速 | 传统方案到同一验收门的关键路径日历时长 ÷ Aegis 到该门的实际关键路径日历时长 | **不可实测**：传统排期未实测，Agent 任务日志不等关键路径 |

| Aegis 专属增益 | “人 + Aegis”对比“同一人 + 直接使用 Codex”的差异 | **不可归因**：没有同题对照或消融实验 |

## 6. 协作机制的额外价值：有工程迹象，暂无独立增量证明

| 机制 | 本案例中的可观察迹象 | 可能形成的收益 | 需要怎样证实增益 |
|---|---|---|---|
| 人类做目标/约束裁决，Agent 执行 | 多轮需求冻结/更改；98 个完成轮次与较少的人类对话输入 | 将人的时间从重复实现转向关键判断 | 完整记录人工审查/返工时长，和同任务人工/直连 Agent 对照 |
| 任务分层与角色独立 | 开发自测、部分 Master/独立审核、受限交付判定分列 | 提升复查覆盖；降低作者自证偏差 | 比较独立审核发现的新增缺陷、严重度和修复成本 |
| 规范/因果/档案关联 | 旧 FAIL、候选版本与替代关系、原 ID、证据边界保留 | 降低跨轮次上下文重建和错误复用 | 比较后续接续任务的恢复时间、误判次数及审核消耗 |
| 自动化测试与回归 | G3/G4/G5 多轮软件行为测试，原 FAIL 不删除 | 缩短复现—定位—修复—验证循环 | 提取每个 defect 的发现时刻、修复时间、复发与逃逸情况 |

| 稳定的质量停点 | G4 延期、C/S INCOMPLETE、正式 A–F STOP 按原范围保留 | 避免把“可运行”误宣称为“生产验收” | 外部审查跟踪漏报、错报和未授权动作数量 |

**重要归因限制：** 上述收益可能同时来自优秀基础模型、Codex Harness、用户的需求裁决、成熟 .NET 生态、Agent 多轮执行和 Aegis 的治理设计。一个全程使用 Aegis 的案例无法把这些因素逐个分离。Aegis 自身的约束还有潜在**额外消耗**：设计审查、证据保存、重复验证、严格拒绝与分支协调。是否值得，要测“降低的缺陷/返工成本是否大于这些额外工时与 Token”，不能只看完成轮次。

### 6.1 交付前质量投入的信号

从日志展示值看，**需求+方案约 12.52 h（28.8%）**、**开发期验证约 12.52 h（28.8%）**，而 **编码研发约 17.55 h（40.4%）**。剩余约 2% 为最终文档整合。此结构说明本次不仅做功能代码，还投入大量时间在需求约束和软件验证中。**它不能独立证明这些验证成本在未来迭代中能够摊薄**；是否摊薄要由后续维护数据确认。[U1]

### 6.2 质量优先可能带来的后续收益（待追踪假说）

- 若前期严格界定控制权限、请求幂等与恢复门，后续新增业务可以降低“先运行、后补保护”的返工风险。
- 若证据和因果记录可复用，跨 Agent/跨会话问题定位可能降低上下文重建成本。
- 若测试与生产真实状态存在差距，软件级质量并不能保证现场缺陷率下降；硬件、正式工艺与正式独立测试仍可能带来大幅补工。

**这三项均是可检验假说，不计入当前 9.21–20.71× 数值。**

## 8. 外部研究用于校准解释，不直接校准本项目 400–900 h

**2025 DORA：** AI 采用与更高交付吞吐关联，但更高的交付不稳定性仍需应对；团队流程和验证能力影响 AI 增益是否能落到最终交付。它支持在效率报告中保留质量和发布门，而不能证明本项目的具体倍数。[E1]

**METR 2026-02：** METR 回顾早期实验并指出，多个 AI Agent 并行时，参与者“花在任务上的时间”测量可能不可靠；晚 2025 工具对部分开发者呈加速趋势，但选择偏差令量化结论较弱。这直接说明本案例应独立记录人类实际投入、Agent 并行和等待结构。[E2]

**NBER 2026 修订稿：** 大样本研究发现 Agent 工具带来的代码活动增幅会在项目与实际发布环节明显收敛。其数值由特定样本与统计设计产生，不可直接换算成本项目的实施时长。对 Aegis 而言，“测试/验收完成的产出”优于 commit、代码行或消息量。[E3]

## 9. 对照验证方案：把案例从宣传材料升级为因果证据

### 9.1 三组相同任务试验

- **A 组：** 熟练工程师 + 常规工具/现成框架，不使用自主编码 Agent。
- **B 组：** 同类工程师 + 原生 Codex Harness/模型，但不接入 Aegis 的组织、规则和证据流程。
- **C 组：** 同类工程师 + Codex/同模型 + Aegis 的组织与约束。

以同一需求冻结、可访问的代码基线、同等部署环境、独立测试门、硬件/生产范围和版本记录评价每组。采用多个相近规模任务、交叉随机分配工程师/任务以抵消技能与题材差异；不让已看过结果的人员直接参与同题复做。**单个任务与单个用户不能排除任务难度和学习效应。**

### 9.2 Aegis 应补采的数据

| 必采字段 | 定义/用途 | 当前状态 |
|---|---|---|
| 真实人类工时 | 决策、编辑、审查、环境处理、实机、返工分别计时；可重叠则归因标注 | 缺失 |
| Agent 树级耗时 | 每节点工作开始/结束、阻塞/等待、并行峰值、关键路径 | 只有汇总日志，定义待核 |
| 模型使用成本 | 每角色/模型输入输出与缓存 Token、工具/计算成本 | 缺失 |
| 质量结果 | 独立门通过率、严重缺陷、逃逸缺陷、30/90 天返工 | 软件阶段部分存在，长期结果缺失 |
| 研发规模与复用 | 生产代码差异、测试代码、第三方复用量、复用起点 | 缺失 |
| 结果证据链 | 源/产物 hash、具体测试候选、历史 FAIL 与覆盖边界 | 文档中已有较好起点，仍需从原始记录机器提取 |
| 效果口径 | 同范围 WBS、系统配置、基准任务难度、独立验收冻结 | 尚未设计对照实验 |

### 9.3 推荐判定方法

**第一阶段：** 本项目标为 `CASE_STUDY / SOFTWARE_STAGE / NO_CONTROL_BASELINE`，保留 43.4508 h、155.1833 h、400/600/900 h 情景、现有测试边界。禁止将 13.81× 作为已证因果加速或成本 ROI。**第二阶段：** 在 6–12 个相近工程任务上补时间、Token、缺陷追踪与独立验收；记录无 Aegis 的 B 组，计算 C−B 变化。**第三阶段：** 至少经历一次功能迭代和维护期，检验 Aegis 严格验证是否真的减少返工及生产缺陷。

## 10. 最终工程评价与可使用的表述

**可使用的结论：** “PROCESS V3 C/S 第一阶段，在人类主导需求与验收约束、Agent 承担大量实现与验证的协作模式下，43 小时 27 分 Agent 任务日志对应一个高可靠性约束的软件阶段交付；包含跨 Windows/Ubuntu 的真实可信连接、多层软件测试和可追溯发布证据。以 400–900 人时的同范围传统研发情景估算，名义工时量级比约 9.2–20.7 倍，中心约 13.8 倍。该数值尚未经人工/裸 Codex 对照校准。”

**不可使用的结论：** “Aegis 研发效率实测提升 14 倍或 200 倍”“相当于替代十几个开发者”“完成生产级工控验收”“所有测试均通过”“Aegis 治理本身带来 14 倍加速”。

**当前优先级最高的补证：** ①还原个人真实累计工时；②导出 Agent 树级时间/Token/成本；③用原生 Codex 与 Aegis 进行相同任务、相同质量门的 A/B 对照。完成三项后，才能把“高产出案例”推进为“可推广的增量效益证据”。
